### Fifth batch: provider-failure and prompt-injection tests

New `tests/adversarial.test.ts` (19 tests) runs against real local D1, a recording fake `fetch`, and a recording fake model.

**Provider failures**
- 401 and 403 map to `denied`, with no retry and no telemetry.
- A 429 is retried and becomes `rate_limited` after 3 attempts.
- A single transient 429 or 503 recovers.
- Repeated 5xx responses become `provider_unavailable`.
- A redirect to a metadata IP is never followed.
- Network failures are contained, and the raw error text is never stored.
- Oversized responses become `response_too_large`; wrong shapes become `schema_mismatch`.
- A missing credential or an unapproved resource makes zero requests.
- The GitHub sync stops at exactly 10 requests (`provider_request_budget`).
- A denied log query keeps metrics as partial evidence.
- Telemetry naming another Worker is refused (`resource_mismatch`).

**Prompt injection**
- Injected Cloudflare log text, URLs, headers and secrets are dropped before storage; unknown outcomes become `unknown`.
- GitHub free text is capped, tag-stripped and redacted.
- An operator note containing "SYSTEM OVERRIDE" instructions changes nothing.
- Investigation model:
  - Injected evidence reaches it only as a JSON value under an unchanged system prompt.
  - A model that "obeys" by citing an unsupplied record is rejected.
  - Echoed secrets and markup are sanitized.
- Chat:
  - Both model calls keep fixed system prompts.
  - Only the seven read-only tools are offered.
  - A poisoned confirmed lesson appears only as user-message data.
  - No configured secret appears in any model payload or in the answer.
  - The incident is unchanged.

**Defects the tests exposed, now fixed**
- `Retry-After: 0` waited a full second; it now uses the 100 ms minimum (`src/providers.ts`).
- Most sync failures were reported as one catch-all `provider_unavailable_or_schema_mismatch`. They now get specific fixed reason codes: request budget, oversized response, resource mismatch, schema mismatch, unavailable. Raw provider messages are still never stored.
- Model output could echo a configured secret in a format the pattern redactor does not recognise. Chat answers and investigation findings now also strip the deployment's own secret values (`withoutSecrets` in `src/sanitize.ts`).

Mutation check: with the old Retry-After handling, catch-all reason and no secret scrubbing restored, 8 of these tests fail.

### Sixth batch: XSS rendering

`scripts/smoke.mjs` now runs a browser XSS pass in its own context with **CSP bypassed**, so only the UI's own escaping protects the page. No new dependencies were needed.

**How it works**
- Every real `GET /api/v1/*` response is intercepted.
- Payloads are planted in every displayed text field, and inside JSON-encoded fields (event payloads, evidence and telemetry summaries, run results, integration config). IDs, statuses and dates are left intact, so the UI behaves normally.
- The assistant view also gets a poisoned stored message.
- Payloads used: `<img onerror>`, an inline `<script>`, an attribute-breaking `"><svg onload>` and a `javascript:` link.

**What it checks**
- It visits all ten pages, the notifications panel and the investigation drawer.
- On every view it asserts:
  - no payload executed (`window.__xss` unset)
  - no injected `img`/`svg`/`script` element and no element with event-handler attributes
  - no `javascript:` link
  - no dialog and no page error
- It also asserts the payload was rendered as visible text: this run showed it on all 10 pages plus the drawer.

**Mutation check:** with chat messages temporarily rendered through `dangerouslySetInnerHTML`, the pass fails with "XSS payload became markup on AI Assistant". The file was restored byte-for-byte afterwards.

**Result:** no XSS defect found. React escaping plus the absence of raw-HTML rendering holds across every view, independently of the server-side `<`/`>` stripping and of CSP.

### Ninth batch: targeted follow-up queries (workflow step 5)

The first summary may now ask for more evidence, and the investigation runs those queries before writing a refined summary.

- **Catalog, not free queries.** `FOLLOW_UPS` in `src/domain.ts`: `probe-history-24h`, `dependency-health`, `recent-deployments`, `worker-logs`. The model names up to two. The server takes the scope, service and time window from the incident. Anything outside the catalog (free text, SQL, URLs) fails validation and the summary is treated as partial.
- **Queries** (`Repository.followUpEvidence`): 24 h probe history (counts, median healthy latency, first and last failure); latest samples and health of up to five registered dependencies; latest current deployment or log telemetry. Missing data is saved as an explicit gap. Results are persisted as `follow-up:*` evidence, guarded on the attempt, so a stale or cancelled attempt writes nothing.
- **Workflow.** Two new steps, `follow-up-queries` and `refined-summary`, run once. The refined call (`…:r2`) is the final round: the prompt and JSON schema no longer offer follow-ups, and any request is dropped. That gives at most two model calls per attempt, both metered against the budget. If the refined summary is unavailable (budget, model failure, cancellation), the first summary stands and `followUps.refined=false` records why. Workflows persists step results, so a retry never re-queries or calls the model again.
- **Fixture mode** asks for `dependency-health` only when the service has registered dependencies, and the refined summary cites the result ("Dependency db is also unhealthy…"). Demo and smoke flows without dependencies are unchanged.
- **UI.** The investigation view lists the follow-up queries that ran and whether the summary was refined. They also appear as persisted evidence.

**Tests:** 5 new tests in `tests/investigation.test.ts`. They drive the real `InvestigationWorkflow.run` through a test-only `cloudflare:workers` stub (vitest alias), with a step runner that caches results like Workflows. Covered:

### Tenth batch: recommendations, cursor pagination, notification delivery, answer streaming

The four remaining spec items are built. Migration `0005_recommendations_delivery.sql` adds the `recommendations` and `notification_deliveries` tables plus page indexes.

**Recommendations as records** (DATA_MODEL `recommendations`)
- A recommendation is either a plain manual step or `{action, rationale, evidenceIds}`. Cited IDs must be ones the model was given.
- When an investigation completes, each recommendation becomes a row: action, rationale, evidence IDs, source, `proposed` disposition, version. It is written only if this call's result is the one persisted, so replays, conflicting completions and stale attempts add nothing.
- Lists show only the current attempt's recommendations.
- `PATCH /incidents/:id/recommendations/:recId` records `accepted`, `rejected`, `done` or `proposed`, with an optional note. Versioned (stale version is 409); another environment's ID is 404. It changes nothing else: EdgeOps never carries out an action.
- Included in the incident detail and the export; purged with closed incidents.
- UI: Accept / Reject / Mark done in the operator review panel.

**Cursor pagination** (`src/pagination.ts`)
- `GET /incidents` (new), `/notifications`, `/knowledge`, `/telemetry` and `/audit` accept `?limit` (1–100) and `?cursor`, and return `meta.nextCursor`. `data` is still the array, so existing clients are unaffected.
- Keyset paging, newest first, ties broken by ID, so pages never repeat or shift when rows arrive mid-walk.
- Cursors are opaque and bound to their list. A cursor from another list, a tampered cursor, an oversized limit or an unknown parameter returns 422.
- The UI still shows the first page; there is no "load more" control yet.

**External notification delivery** (F19, `src/notify.ts`)
- Destinations come only from the deployment secret `NOTIFICATION_WEBHOOKS` (`[{scope,url,format: json|slack}]`), never from the API or the model, because a webhook URL is both a credential and an outbound target. Invalid configuration means no destinations.
- URL policy: HTTPS on the default port, a public DNS name, no credentials or fragment. DNS resolution is checked against the probe SSRF rules.
- Delivery: scheduled maintenance enqueues notifications from the last 24 h into an outbox keyed by notification and destination, so each is delivered once and configuring a destination never replays history. Each attempt is claimed before it is sent, so concurrent runs cannot both send.
- Retries: 429, 5xx, timeouts and network errors retry with backoff (5, 10, 20, 40 min), capped at 5 attempts. Other 4xx responses and denied destinations fail permanently.
- Payload: title and identifiers only, never evidence, sent with an `Idempotency-Key` header.
- Rows store a SHA-256 key, never the URL, and `withoutSecrets` scrubs configured webhook URLs from model output.
- `GET /notifications/destinations` and a Settings card show the host and sent/pending/failed counts.

**Incremental answer streaming** (F06; opt-in `AI_STREAMING=on`, default off)
- Workers AI JSON mode does not stream, so the streamed answer is plain text followed by an `EVIDENCE:` / `UNKNOWNS:` trailer.
- `ProvisionalText` releases only whole sentences or lines, each redacted on its own. It holds back unfinished sentences, open private-key blocks, fragments that end in a credential-introducing word, and the trailer.
- When the stream ends, the trailer is parsed and every citation is checked against the allowed IDs.
- If validation fails or the context changed, the agent sends a `retract` frame and the client discards the provisional text. The saved, fully validated answer always replaces what was shown.
- With streaming off, the validated JSON path is unchanged.
